This guide assumes no prior Tari or Ootle experience. It starts from downloading the wallet daemon on a blank server and ends with a completed test payment in WooCommerce. Every link is clickable. Every command is copy-paste ready.

Before you start
You need: a Linux/macOS/Windows server with a shell · PHP 7.4+ with curl enabled · WordPress 6.0+ with WooCommerce 6.0+ installed · outbound HTTPS access to the Ootle indexer and your wallet daemon · testnet tTARI (free from the faucet) or real TARI for production.

1Overview — how the pieces fit together

The plugin is one of three moving parts. WooCommerce handles the storefront and orders. The wallet daemon holds your keys and signs transactions. The indexer reads on-chain state and streams events. Nothing works until all three are running and reachable.

Figure 1 — System Architecture: WooCommerce → Wallet Daemon → Ootle Network

Checkout flow, end to end: customer clicks "Pay with Ootle" → plugin calls the wallet daemon's JSON-RPC to create a payment → customer pays on the Ootle network → an OrderPlaced event lands in the indexer → your webhook listener POSTs to ?wc-api=ootle_webhook → the plugin verifies the signature and marks the order complete.

2Install the Ootle wallet daemon

The wallet daemon is the only process that holds your private keys. It signs every transaction the gateway sends. Everything else is read-only. Run it somewhere your WordPress server can reach over the network, and nowhere else.

2.1 · Download the wallet daemon

The release ships a standalone tari_ootle_walletd binary per platform. Note: there is no tari_ootle_wallet_cli binary in the release — the CLI is not published as a prebuilt asset. You interact with the daemon directly over JSON-RPC (which is what the plugin does).

PlatformAsset filename (v0.45.0)
Linux x86_64tari_ootle_walletd-0.45.0-9c62606-linux-x86_64
Linux arm64tari_ootle_walletd-0.45.0-9c62606-linux-arm64
macOS arm64 (Apple Silicon)tari_ootle_walletd-0.45.0-9c62606-macos-arm64
Windows x64tari_ootle_walletd-0.45.0-9c62606-windows-x64.exe

Get the current filenames and hashes from the releases page — the build hash (9c62606) changes with each release.

2.2 · Choose your network

NetworkFlagUse caseFunds

Mistakes on testnet cost nothing. Get the entire flow working on esmeralda first, then repeat the same steps on mainnet with a fresh, funded account and a production API key.

2.3 · Start the daemon

This command runs the daemon on the esmeralda testnet, bound to localhost so only this machine reaches it. The web UI is served on the same host at port 5100.

Shell Start the wallet daemon on testnet
tari_ootle_walletd --network esmeralda --listen-on 127.0.0.1:5100 --authentication none --enable-vite-dev-port 5173
OptionMeaning
--network esmeraldaConnect to the esmeralda testnet (the default). Use mainnet for production.
--listen-on 127.0.0.1:5100Bind address. Use 127.0.0.1:5100 if the plugin runs on the same machine; 0.0.0.0:5100 to accept remote connections.
--authentication noneDisables WebAuthn passkey login so you can drive the daemon over JSON-RPC. Test/disposable wallets only.
--enable-vite-dev-port 5173Sets the WebAuthn origin to http://localhost:5173 and enables permissive CORS — fixes the "invalid domain" error in the web UI.
Default ports5100 = JSON-RPC + web UI (the plugin connects here)
Security warning you must read
The command above runs without additional daemon-level authentication — appropriate only for a disposable testnet wallet. The daemon logs a loud warning saying so, and it is correct. Never expose an unauthenticated daemon holding real value. In production, keep the daemon bound to 127.0.0.1 or a private network, and front it with an HTTPS reverse proxy plus a firewall.

Open http://localhost:5100 in your browser to reach the wallet web UI — create accounts, check balances, claim testnet funds, and manage API keys from there.

3Create an account and fund it

3.1 · Create a merchant account

There is no wallet CLI binary in the release — you drive the daemon over its JSON-RPC endpoint. First bootstrap a bearer token (with --authentication none, this needs no passkey), then create the account.

Shell Bootstrap an Admin token and create the merchant account
# 1. Bootstrap an Admin bearer token (auth=none: no passkey, no WebAuthn)
TOKEN=$(curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"auth.request","params":{"permissions":["Admin"],"credentials":{"None":null}},"id":1}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['result']['token'])")

# 2. Create the merchant account (returns the account + its Ootle address)
curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","method":"accounts.create","params":{"name":"merchant"},"id":2}' \
  | python3 -m json.tool

Note the owner_public_key and the otl_esm_… address from the response — you paste the public key into the plugin's Merchant Public Key field later.

Why {"None":null}?
Under --authentication none, auth.request expects a tagged enum credential. {"None":null} is the variant that satisfies it — this is the documented bootstrap that replaces the WebAuthn passkey flow, and it is what makes the "invalid domain" error irrelevant for programmatic access.

3.2 · Claim testnet funds (testnet only)

Two ways, both free on esmeralda:

MethodHow
Web UIClick "Claim Testnet Funds" at http://localhost:5100
JSON-RPCCall accounts.create_free_test_coins against the daemon (below)

The account argument is a tagged enum, not a bare name — pass the component address as {"ComponentAddress":"…"}. A claim also needs a max_fee.

Shell Claim testnet funds
ADDR="component_4293145b…"  # your account's component_address
curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d "{\"jsonrpc\":\"2.0\",\"method\":\"accounts.create_free_test_coins\",\"params\":{\"account\":{\"ComponentAddress\":\"$ADDR\"},\"max_fee\":1000},\"id\":3}"
Faucet can be empty — check first
The shared esmeralda faucet runs dry. Before claiming, check it: accounts.get_faucet_balance returns balance and claim_amount. If balance < claim_amount the claim fails with "the testnet faucet does not hold enough funds." That is a testnet top-up issue on Tari's side, not a client bug — ask in the Tari Discord #development channel and retry once refilled. The alternative is claiming tTARI by burning XTM on L1, which needs real funds.

3.3 · Confirm your balance

Shell Confirm the account has a non-zero balance
curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d "{\"jsonrpc\":\"2.0\",\"method\":\"accounts.get_balances\",\"params\":{\"account\":{\"ComponentAddress\":\"$ADDR\"}},\"id\":4}" \
  | python3 -m json.tool

You must see a non-zero balance before moving on. An empty account cannot pay transaction fees, and every Ootle transaction pays fees in TARI.

4Mint an API key

The plugin authenticates to the wallet daemon with a long-lived, permission-scoped API key. An Admin mints it once; the plugin then presents it as a Bearer token on every JSON-RPC call. There is no interactive login, no JWT exchange, and no session to refresh.

4.1 · How the key works

AspectDetail
Format32 random bytes, prefixed with tw_, base64-encoded
ShownExactly once at creation — the daemon cannot display it again
StoredOnly a SHA-256 hash — a database leak does not expose the key
Sent asAuthorization: Bearer tw_... on every request
RevocationImmediate — the next request after revoke fails, no cache
Copy it the moment it appears
The raw key is displayed once, in the creation dialog, and then never again. Close the dialog and it is gone. Paste it directly into your password manager — not a text file, not a ticket, not chat.

4.2 · Choose the smallest scope set

Grant only the permissions the plugin actually needs. An agent cannot self-promote: permissions come from the stored key row, not from anything the plugin sends.

Plugin roleRecommended scopes
Monitoring onlyAccountInfo, TransactionGet
Full payment gatewayAccountInfo, TransactionSend_<your-account>, TransactionGet
Never grant Admin by default
Admin lets the key mint, list, and revoke other keys. Grant it only with a deliberate reason, and only with the explicit confirmation flag. For a payment gateway, the transaction-send scope for your one merchant account is enough.

4.3 · Create the key via Web UI (optional)

The web UI works too, but only if WebAuthn can reach it — open http://localhost:5100/api-keys and log in via passkey. If you hit an "invalid domain" error (WebAuthn rejects non-localhost origins), use the JSON-RPC method in 4.4 instead — it needs no browser at all.

Navigate to API KeysGo to the /api-keys route in the wallet web UI.
Click Create API KeyGive it a friendly name, e.g. wordpress-gateway.
Enter the scopesPaste the comma-separated scope list from the table in 4.2.
Set an expiry (recommended)Prefer the shortest expiry that fits. A leaked short-lived key dies on its own without manual revocation.
Copy the raw key immediatelyIt appears once, with a copy button. Store it before dismissing the dialog.

4.4 · Create the key over JSON-RPC (no CLI, no passkey)

With --authentication none, mint the key directly against the daemon using the bootstrap token. The raw key prints to the response once — pipe it straight into your secret store.

Shell Mint an API key for the WordPress gateway
# Basic key with two scopes
curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","method":"auth.create_api_key","params":{"name":"wordpress-gateway","permissions":["AccountInfo","TransactionGet"]},"id":3}' \
  | python3 -m json.tool

# With an expiry (unix seconds; None = never)
curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","method":"auth.create_api_key","params":{"name":"wordpress-gateway","permissions":["AccountInfo","TransactionGet"],"expires_at":1893456000},"id":4}' \
  | python3 -m json.tool

# Granting Admin requires the explicit confirm_admin flag
curl -s -X POST http://127.0.0.1:5100/json_rpc -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","method":"auth.create_api_key","params":{"name":"full-access","permissions":["Admin"],"confirm_admin":true},"id":5}' \
  | python3 -m json.tool
TaskRPC method
List keysauth.list_api_keys — metadata only, never raw keys
Revokeauth.revoke_api_key with {"id":<n>} — effective immediately

4.5 · What the daemon protects you from

  • Wrong, revoked, or unknown key — identical error message and timing for all three; an attacker cannot enumerate valid hashes.
  • Out-of-scope request — the stored scope set is enforced against every endpoint; the request fails with InsufficientPermissions.
  • Non-admin minting keys — rejected; only Admin reaches the key-management endpoints.
  • Expired key — silently filtered out; the next request fails exactly like a revoked key.

Log into WordPress adminAny account with plugin-install privileges works.
Go to Plugins → Add New → Upload PluginChoose the ootle-payment-gateway.zip file and click Install Now.
Activate the pluginClick Activate Plugin after installation completes.
Confirm WooCommerce is activeThe plugin requires it and silently does nothing without it. The gateway appears under WooCommerce → Settings → Payments automatically — no code edits needed.
What activation does
The plugin registers itself under gateway id ootle via the woocommerce_payment_gateways filter and flushes rewrite rules so the webhook endpoint resolves. Nothing else is written to your database until you save the settings.

6.1 · Finding your API base URL

Daemon locationAPI Base URL value
Same machine as WordPresshttp://127.0.0.1:5100
Separate server on your LANhttp://192.168.x.x:5100
Remote VPS with a domainhttps://ootle.yourdomain.com (reverse-proxy the daemon)
Production must use HTTPS
In production, always front the daemon with a reverse proxy (nginx or Caddy) and a valid certificate, so the API key is never sent over plain HTTP. Test Mode disables SSL verification — it must be off in production.

6.2 · Generate a webhook secret

Run this in your terminal and paste the output into the Webhook Secret field. This secret signs outgoing webhook payloads so the plugin can prove they came from a trusted source. It is never sent to the wallet daemon.

Shell Generate the webhook secret
openssl rand -hex 32

7Connect the webhook

Without a webhook, orders stay in "pending" forever — the plugin never learns the payment succeeded. Your indexer listener (or any monitoring service) must POST to the endpoint below whenever an on-chain payment event matches an order.

ItemValue
Webhook URLhttps://yoursite.com/?wc-api=ootle_webhook
MethodPOST
Content-Typeapplication/json
Auth headerX-Ootle-Signature: HMAC-SHA256 of the raw body, keyed with your webhook secret

The payload carries an event type and a session id. The plugin looks up the order by session id and updates its status. Six event types are supported:

EventEffect on the order
payment.completedCompleted payment_complete() — transaction hash logged
payment.failedFailed order marked failed
payment.cancelledCancelled order marked cancelled
payment.refundedRefund WooCommerce refund created, hash stored
dispute.createdNote dispute note added to order
dispute.resolvedResolved order updated per ruling
No listener yet?
Orders remain pending, which is expected. The payment flow still works — you complete orders manually from WooCommerce → Orders until the listener is running.

9Going to production

9.1 · Pre-launch checklist

  • Switch the network — restart the daemon with --network mainnet.
  • Turn off Test Mode — uncheck it in plugin settings so SSL verification is enforced.
  • Update the API Base URL — point at your production daemon endpoint.
  • Use HTTPS — front the daemon with a reverse proxy and a valid certificate.
  • Rotate the API key — mint a production key with production scopes; revoke the testnet key.
  • Set a key expiry — long but finite, so a leaked key eventually dies.
  • Fund the account — confirm the merchant account has mainnet TARI for fees.
  • Place one live order — a small real purchase before announcing the gateway.

9.2 · Security rules that are not optional

RuleWhy
Never run an unauthenticated daemon with real fundsAnyone who can reach the port can drain the account
Never commit the API key or webhook secretVersion control history is permanent
Use the smallest scope set possibleA leaked read-only key cannot drain the account
Set key expiryLimits how long a leaked key is useful
Revoke unused keysFewer live keys means less attack surface
Firewall the daemon portOnly the WordPress server should reach port 5100
